# 后端与智能合约接口清单

本清单由 `业务服务_greenhouse-api` 的控制器与 `智能合约_contracts` 的合约源码核对后整理，路径、权限和函数签名与实际实现一致。

## 1. 认证与通用约定

- 登录接口 `POST /api/auth/login` 使用数据库账号换取 JWT；其余接口支持 JWT 或 HTTP Basic（物联网服务使用 `iot-service` 服务账号走 Basic）。
- 统一响应结构为 `{ code, message, data, requestId }`，`code = 0` 表示成功。
- 公开接口仅限：登录、健康检查、溯源码查询、田块指针链查询；其余接口均需认证。
- 写接口必须携带业务主键与操作者，重复提交同一周期或同一合格证时按幂等处理。

环境周期存证覆盖范围（`EnvironmentService` + `EnvironmentMetrics`）：

- 一个环境周期必须同时具备 `temperature`、`humidity`、`light`、`soil_moisture` 四项读数，缺任意一项时 `POST /api/environment/cycles` 返回 400、`POST /api/environment/cycles/attest` 返回 409，不生成摘要与根哈希。
- `dataDigest = SHA-256(温室编码 | 周期起止 | 每项读数的设备、指标、值、单位、采集时间)`；`rootHash = SHA-256(dataDigest + 上一周期根哈希)`，四项指标全部计入摘要。
- 链上只保存 `rootHash` 与 `dataDigest` 元数据，原始读数留在链下数据库；消费者打开 `/trace?code=…` 时，公开接口会返回该温室最近一次环境周期的四项读数、周期起止时间、根哈希与链上状态，用于扫码核对。

## 3. MQTT 主题

物联网服务默认 `app.mqtt.mode=logging`（只打印不连代理），把模式改为 `broker` 后连接 `app.mqtt.broker-url`（默认 `tcp://localhost:1883`）并收发以下主题；`MqttMessageRouter` 按主题后缀把上行消息分别交给遥测、设备状态和指令回执三条处理链：

| 主题 | 方向 | 数据 | QoS |
| --- | --- | --- | --- |
| `iot/{greenhouseCode}/{deviceCode}/telemetry` | 上行 | 温度、湿度、光照、土壤水分等指标读数 | 1 |
| `iot/{greenhouseCode}/{deviceCode}/status` | 上行 | 在线状态、设备自检、故障码 | 1 |
| `iot/{greenhouseCode}/{deviceCode}/command` | 下行 | 指令编号、指令类型、参数与超时时间 | 1 |
| `iot/{greenhouseCode}/{deviceCode}/ack` | 上行 | 指令编号、执行结果、执行时间 | 1 |

处理链路：

- 遥测：`TelemetryIngestService` 标准化后由 `RestTelemetryForwarder` 调用 `POST /api/iot/telemetry/readings`，同时刷新设备最后在线时间。
- 设备状态：`DeviceStatusIngestService` 调用 `POST /api/iot/devices/status`，更新 `device.online_status` 与 `last_seen_at`。
- 指令下发：`CommandDispatchService` 每 3 秒轮询 `GET /api/control/commands/pending`，发布到命令主题后调用 `POST /{commandNo}/dispatch`；发布失败不标记，下一轮自动重试。
- 设备回执：`CommandAckIngestService` 调用 `POST /api/control/commands/{commandNo}/ack`，状态收敛为 `SUCCEEDED`/`FAILED`。

演示环境不依赖 MQTT Broker：`demo` 配置直接按周期写入遥测，也可以用 `开发脚本_scripts/模拟设备_telemetry-simulator.ps1` 上报遥测、`开发脚本_scripts/模拟设备_command-simulator.ps1` 模拟设备回执。指令超时由业务服务的 `ControlCommandJob` 扫描处理（先重试，超过上限置 `FAILED`）。

## 5. 链上链下边界

| 数据 | 存放位置 | 说明 |
| --- | --- | --- |
| 原始环境读数、检测报告文件 | 链下（数据库与文件服务） | 高频、体积大，不上链 |
| 环境四项指标（温度/湿度/光照/土壤水分） | 链下数据库；摘要入链 | 周期存证前强制四项齐全，`dataDigest` 覆盖四项读数的设备、值、单位与采集时间 |
| 周期根哈希、合格证摘要、溯源码签名摘要、扫码记录、追溯节点摘要 | 链上 | 仅保存摘要与必要元数据，用于多方核验 |
| 用户、批次、设备、计划等业务数据 | 链下 | 通过业务主键与链上记录关联 |

后端在调用合约前完成权限、状态和格式校验，合约再按调用账户校验角色，两侧都不省略。

链上调用统一走 `integration/chain/ChainGateway`。已接入并写回回执（交易哈希、区块高度、状态）的流程有五个：环境周期入库（`recordEnvironmentRoot`）、合格证备案（`recordCertificate`）、生成一物一码（`registerTraceCode`）、消费者扫码（`appendScanRecord`）、追加田块追溯节点（`appendTraceNode`）。追溯节点按指针顺序补链，链上不可用时保留待补偿。

网关有两种实现：`RestChainGateway`（`app.chain.mode=rest`，默认，调用链上适配服务把交易写入真实链）与 `SimulatedChainGateway`（`app.chain.mode=simulated`，本地确定性回执，仅供自动化测试使用）。适配服务实现见 `platform/智能合约_contracts/链上适配服务_chain-adapter-fisco/ChainAdapter.java`，基于 FISCO BCOS Java SDK 2.9.1。`rest` 模式的适配服务协议为：

```json
POST /chain/adapter
{"method": "recordEnvironmentRoot", "arguments": {"cycleId": "1001", "rootHash": "…", "metadata": "…"}}

200 OK
{"transactionHash": "0x…", "blockNumber": 1284700, "status": "CONFIRMED"}
```

方法名与合约函数一一对应，适配服务只负责交易签名与合约调用，替换实现时业务代码不变。`GET /health` 返回 `{status, mode, contractAddress}` 用于联通性检查；链上交易失败时适配服务返回 `{"message": "…"}`，后端 `ChainInvoker` 捕获后写入 `PENDING` 状态，不回滚业务数据。

三个写方法（`recordEnvironmentRoot`、`recordCertificate`、`registerTraceCode`）按业务标识幂等：同一标识内容摘要一致时允许重复上链，摘要不一致时链上回滚，避免链上记录被覆盖。`appendTraceNode` 按「田块 + 下标」幂等：同下标摘要一致为幂等重放，下标等于链上长度时按 `previousHash` 顺序追加，跳序或改写历史会被拒绝。

## 一物一码二维码（ZXing）

二维码由后端用 ZXing（`com.google.zxing:core` + `javase` 3.5.3）生成，前端用 `qrcode.vue` 做预览，两边的字符串都来自同一个接口，避免"预览和打印不一致"。

**码内只放公开校验地址，不放追溯明细。** 追溯数据量大、还会随链上状态变化，塞进二维码既装不下也容易过期；扫码后由前端再向后端查询，结合 FISCO BCOS 根哈希、电子合格证与追溯节点做校验。

扫码落地页除合格证与追溯节点外，还会展示该溯源码所属温室的**最近一次环境周期存证**：温度、湿度、光照、土壤水分四项读数的值与单位、采集时间、周期起止时间、根哈希与链上状态，并明确标注四项是否全部计入根哈希。环境数据来自 `/api/trace/{code}` 的 `environment` 字段，页面不额外请求内部接口。

两种内容形式由 `app.trace.qr.mode` 切换：

| 模式 | 内容 | 说明 |
|---|---|---|
| `query`（默认） | `https://域名/trace?code=产品编码` | 指向消费者公开落地页（前端 `/trace` 路由）；部署时把 `TRACE_PUBLIC_BASE_URL` 换成实际域名 |
| `gs1` | `https://域名/01/{GTIN}/21/{序列号}` | 需配置真实 GS1 厂商识别码 `TRACE_GS1_COMPANY_PREFIX`；未配置时自动回退为 `query` |

配置项（`application.yml` → `app.trace.qr`）：

| 变量 | 默认值 | 用途 |
|---|---|---|
| `TRACE_PUBLIC_BASE_URL` | `https://greenhouse.example.com` | 写进二维码的公开地址，**部署前必须改** |
| `TRACE_QR_MODE` | `query` | `query` 或 `gs1` |
| `TRACE_QR_QUERY_PATH` | `/trace` | 消费者扫码后打开的前端路径（公开只读页，无需登录） |
| `TRACE_GS1_COMPANY_PREFIX` | 空 | GS1 厂商识别码，仅 `gs1` 模式使用 |
| `TRACE_QR_SIZE` | `320` | 默认出图边长（像素），请求可用 `?size=` 覆盖，限制 96–1024 |

GTIN-14 的校验位按 GS1 标准（自右向左 3、1 交替加权）计算；未拿到真实厂商识别码时，`gs1` 模式下的商品项目代码由产品编码数字推导，属于演示映射，接入真实 GS1 前缀后即符合标准。

图片接口对匿名开放：二维码里只有公开地址，本身不敏感，浏览器直接点下载链接也能取到（否则 `<a download>` 不会带 JWT，会 401）。两个接口都会校验产品编码是否存在，不存在返回 404。
