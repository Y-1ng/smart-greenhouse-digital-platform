| 待下发列表 | `GET /api/control/commands/pending` | 返回该指令，含温室、设备、指令类型与参数 |
| 标记已下发 | `POST /api/control/commands/{commandNo}/dispatch` | `status=DISPATCHED`，`dispatchedAt` 非空；同一指令不再出现在待下发列表 |
| 已下发列表 | `GET /api/control/commands/dispatched` | 返回该指令，供设备模拟器或运维排查 |
| 设备回执 | `POST /api/control/commands/{commandNo}/ack` | `status=SUCCEEDED`，`completedAt` 非空，设备 `operating_state` 同步更新 |
| 超时重试 | `ControlCommandService.applyTimeouts` | 超时后 `status=CREATED`、`retry_count=1`、`failure_reason` 记录重试次数 |
| 重试上限 | 同上 | 再次超时后 `status=FAILED`，原因“超过 2 次尝试仍未收到设备回执” |

### 10.2 物联网服务链路（单元验证）

| 验证点 | 实测结果 |
| --- | --- |
| 主题路由 | `telemetry`/`status`/`ack` 三种主题分别路由到对应处理链，未识别主题只记日志 |
| 设备状态报文 | 解析 `online`、`message` 后转发 `/api/iot/devices/status` |
| 指令回执报文 | 解析 `commandNo`、`success`、`executedAt` 后转发 `/api/control/commands/{commandNo}/ack`；缺 `commandNo` 时不转发 |
| 指令下发 | 按模板拼出 `iot/{温室}/{设备}/command`，载荷含指令编号与类型，成功后回写已下发 |
| 下发失败 | Broker 异常时不标记已下发，下一轮轮询会重新取到该指令 |
| 接口契约 | 用业务服务真实响应结构（含 `operator`、`status`、`retryCount` 等多余字段）解析待下发指令成功 |

### 10.3 三进程真实端到端验证（2026-09-19 补测）

业务服务由本机后端实例承担，物联网服务以「无 Web 容器」方式启动（装配真实定时任务，MQTT 走日志网关），设备侧由 `模拟设备_command-simulator.ps1` 扮演。全程用真实 HTTP 调用，无任何桩替换：

| 阶段 | 时间 | 实测结果 |
| --- | --- | --- |
| 生成指令 | 19:34:23 | `POST /api/control/commands` → `status=CREATED`，`timeoutSeconds=90` |
| 物联网服务下发 | 19:35:00 | 轮询到待下发指令，发布命令报文并回写 `POST /dispatch` → `status=DISPATCHED` |
| 设备回执 | 19:35:34 | 模拟器调用 `POST /ack` → `status=SUCCEEDED`，`completedAt` 落库，`retryCount=0` |
| 设备状态同步 | 19:35:27 | 设备 `FAN-A-02` 变为 `onlineStatus=ONLINE`、`operatingState=ON`（回执触发运行状态更新） |
| 超时重试 | 19:36:13 | 另一条 `timeoutSeconds=10` 且不下发的指令被扫描到 → `retryCount=1`，`failureReason=指令超时未收到回执，第 1 次重试` |
| 超过重试上限 | 19:36:21 | 再次超时 → `status=FAILED`，`failureReason=超过 2 次尝试仍未收到设备回执` |

结论：`CREATED → DISPATCHED → SUCCEEDED` 与 `CREATED → 重试 → FAILED` 两条路径都在真实进程中跑通，前端调用的就是这两个接口，因此界面轮询到的状态迁移与后端一致。
